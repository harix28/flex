# PostgreSQL foundation — Phases 2 through 5

Implemented and verified with PostgreSQL 18.4, Python 3.12.15 on Windows.
Current head is `0004_replay`; see [registry migration/operations](../docs/MACHINE_SENSOR_REGISTRY.md). Phase 3 revision is `0002_auth`; [authentication documentation](../docs/AUTHENTICATION.md) describes its additive changes and rollback risks.
The immutable initial Alembic revision is `0001_registry`. It creates only tenants,
users, memberships, machines, sensors and installations, plus Alembic bookkeeping.
`database/reference/schema.sql` remains a future design, not an executable setup.

## Local setup and operation

The existing PostgreSQL 18 binaries at `C:\Program Files\PostgreSQL\18\bin` are reused.
The pre-existing PostgreSQL Windows service is untouched. Docker CLI exists but its
engine is unavailable; Docker is not required for this native setup. On another
machine install PostgreSQL 18 with its `btree_gist` extension, Python 3.12, and the
pinned requirements. Run from the project root:

```powershell
.\.venv\Scripts\python.exe scripts/postgres-local.py start --bin 'C:\Program Files\PostgreSQL\18\bin'
.\.venv\Scripts\python.exe -m sentinel.db upgrade --env-file .runtime/postgres.env
.\.venv\Scripts\python.exe -m sentinel.db check --env-file .runtime/postgres.env
# Explicit optional sample data, safe to repeat:
.\.venv\Scripts\python.exe -m sentinel.db seed-demo --env-file .runtime/postgres.env
```

The helper initializes only a new `.runtime/postgres-phase2` cluster, with a random
password stored in an ACL-restricted `.runtime/postgres.env`; SCRAM authentication
and IPv4 loopback port 55432 are used. It never deletes/resets a cluster, overwrites
the application's `.env`, or changes the existing PostgreSQL service. A port conflict
must be resolved explicitly. All `.runtime` contents are ignored. The helper's
`meridian_local` role is a local development superuser, not a production runtime role.
For a managed database provide your own private `DATABASE_URL` and use the same CLI.

To connect the existing API while retaining its existing key/model configuration:

```powershell
$env:DATABASE_URL = (Get-Content -LiteralPath .runtime/postgres.env | Where-Object { $_.StartsWith('DATABASE_URL=') }).Substring(13)
.\scripts\start-local.ps1
# Another terminal: .\scripts\check-local.ps1
```

Do not print the environment value. Alternatively store the URL privately in the
existing `.env`. Process environment wins, including a blank override. URL format:
`postgresql+psycopg://USER:PERCENT_ENCODED_PASSWORD@HOST:PORT/DATABASE`. Query options
are rejected to keep timeout policy fixed. Blank URL disables database integration;
inference remains usable. Settings representations, HTTP errors and operator CLI
failures omit credentials. Do not enable SQL/driver debug logging with real data.

Stop the API with Ctrl+C; its lifespan disposes the pool. Stop only this cluster:

```powershell
.\.venv\Scripts\python.exe scripts/postgres-local.py stop --bin 'C:\Program Files\PostgreSQL\18\bin'
Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
```

Data is retained across stop/start. Connections use a pool of five, no overflow,
three-second pool/connect/lock timeouts and a five-second statement timeout. SQLAlchemy
sessions commit on successful context exit and roll back/close on exceptions.
`/health/database` is 200 only with the expected migration revision, otherwise 503
with a safe code. `/health/ready` remains model readiness; `/health/live` is liveness.
Readiness checks revision/connectivity, not exhaustive detection of manual schema drift.

## Reviewed Phase 2 schema choices (Phase 3 changes linked above)

- UUIDs are generated by PostgreSQL by default. All six entities have timestamptz
  creation timestamps; connections use UTC.
- External identities remain global with unique issuer/subject pairs. Memberships
  provide explicit tenant ownership and unique tenant/user pairs. No passwords or
  authentication sessions are created.
- Roles retain the reference's additive text array, constrained to a nonempty set
  of viewer, technician, manager, ml_engineer and admin, without null elements.
  Gateway is a future credential principal, not a human membership role.
- Machines/sensors keep tenant-scoped codes. Composite tenant foreign keys protect
  installations and verifier membership. Required text cannot be blank. Deletes use
  restrictive foreign keys; the repository provides retirement rather than deletion.
- Installations use finite bounds and half-open `[valid_from, valid_to)` intervals;
  null end is unbounded. A GiST exclusion with `btree_gist` prevents all overlapping
  sensor periods, including concurrent writes and closed historical periods.
  Adjacent installations are allowed. Verification actor/time must be paired.
- Added timestamps, nonempty checks, role checks, verification consistency, version
  positivity, relevant FK indexes and the exclusion constraint tighten the reference.
  Deferred telemetry, sessions, workflows and other future tables are deliberately absent.

The exclusion design follows PostgreSQL's [range documentation](https://www.postgresql.org/docs/18/rangetypes.html);
transaction scope follows [SQLAlchemy session guidance](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).

## Tenant boundary and Phase 3 handoff

`RegistryRepository(session, tenant_id=UUID(...))` requires explicit context; reads
and retirement include tenant predicates, and writes derive ownership from that
context. Cross-tenant object reads return no record. Composite FKs enforce association
boundaries even with direct SQL. This context is NOT authenticated identity. There
are no registry CRUD routes. Phase 3 organization endpoints derive context from verified
sessions. Raw SQL credentials remain privileged: no RLS or production grants are claimed. Global tenant/user provisioning and demo seed are
operator operations, not tenant-facing APIs.

Phase 3 now implements local password sessions/CSRF, authenticated membership
resolution and additive roles for organization resources. OIDC and registry routes remain future work. Never
trust a tenant UUID from a request as identity. Add a least-privilege runtime role,
separate migration credentials, audit, backup/restore validation and deployment TLS
configuration before production. Existing local API-key inference is unchanged.

## Migrations, rollback and restore

Normal upgrade: `python -m sentinel.db upgrade` (loads private `.env` / environment).
Alembic also supports `python -m alembic upgrade head`, `current`, `history` and
`upgrade head --sql` from the root. The operator wrapper sanitizes failures.
There is no automatic startup migration or destructive operator wrapper.

**`python -m alembic downgrade base` permanently drops all six foundation tables and
all their records.** Use only on an explicitly disposable database. Never point this
command at development/production data. The extension is retained because other
schemas may use it; dependent objects block drops (no CASCADE). Re-upgrade recreates
empty tables; it does not restore data. For a non-test rollback, take an access-controlled
`pg_dump` backup first, preserve it outside the repository, and restore/validate into
a separate database before switching configuration. Production backup/restore has
not been exercised in Phase 2. Do not automatically reset a failed migration.

## Real PostgreSQL tests

```powershell
# Existing behavior and database-independent tests:
.\.venv\Scripts\python.exe -m pytest -q -m 'not postgres'
# Explicit opt-in administrative connection, never printed:
$env:SENTINEL_TEST_ADMIN_URL = (Get-Content -LiteralPath .runtime/postgres.env | Where-Object { $_.StartsWith('DATABASE_URL=') }).Substring(13)
.\.venv\Scripts\python.exe -m pytest -q -m postgres
Remove-Item Env:SENTINEL_TEST_ADMIN_URL
```

The test role needs CREATEDB and permission to install `btree_gist`. Each test creates
its own `meridian_test_<random UUID>` database, migrates it, and drops only that exact
generated database in cleanup. It never downgrades or clears `meridian_dev` or the
provided URL's database. Tests do not read development `.env`; absent explicit test
URL means PostgreSQL tests are visibly skipped. Interrupted runs may leave a generated
test database; inspect ownership and name before any manual cleanup. Never bulk-drop
matching databases. No SQLite substitution is used.


Phase 4 preserves the six foundation tables, extends machine/sensor provenance fields,
adds installation slot exclusion and guard triggers, and extends the existing audit table.
Registry endpoints now validate session-derived membership before repository access.
See docs/MACHINE_SENSOR_REGISTRY.md for migration failure/rollback handling and legacy
unclassified records. No inference or ingestion is triggered by registration.


## Phase 5 implemented extension (2026-10-26)

Current migration is `0004_replay`. `sentinel/ingestion/` implements persistent NASA
replay observations, immutable partition/file-version streams, atomic batches and
bounded history/quality APIs with the existing sessions, CSRF and tenant permissions.
The authoritative new contract is `docs/REPLAY_INGESTION.md`; Phase 6 integration
details are in `docs/PHASE5_HANDOFF.md`. Older phase-specific text above is historical.
Machine source bindings now accept `split: train|test` and optional `file_sha256`
(required for new train registrations). Different trajectory/version requires a new
machine. No prediction persistence or physical-device ingestion was implemented.
